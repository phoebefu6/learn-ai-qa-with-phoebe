Generating tests

This is not the session where somebody tells you generated tests are bad. They are genuinely useful, at real industrial scale, with published numbers. It is the session where you learn that the order you do it in decides whether they help or hurt, and that the gap between the two orders is roughly double. Tonight you generate tests for your own module twice, once from the code and once from the specification you wrote for homework, and compare what each one catches.

Recap

Why the specification homework mattered

Session 2 asked you to write down what your module promises: inputs, outputs, thresholds, error cases, half a page. That document is the input to tonight's most important experiment, and without it half of this session is a spectator sport.

🎫 Clear all three quiz questions to stamp your passport Live = presented in the 45 minutes Self-study = the full depth, after class

★ What you walk out with tonight. Two generated test sets for the same module, produced in two different orders, and a measured difference between them. Plus one rule that costs nothing to adopt and is backed by two independent studies.

LiveThe whole session in one sentence3 min▶

Generate the test from the specification, not from the implementation. That is the rule. Everything else tonight is either the evidence for it or the machinery around it.

The reason it works is uncomfortable once you see it. When a model reads your finished code and writes tests for it, it is not checking your code against anything. It is describing your code back to you in the shape of assertions. If the code is right, you get a fine test. If the code is wrong, you get a test that carefully encodes the bug as the expected behaviour, goes green, and now defends the bug against anyone who tries to fix it.

Real world

This is why a generated suite can go from zero to high coverage in an afternoon and catch nothing the following week. It was never given anything to compare the code against. Session 1 showed you a suite like that with a mutation score of 25.

Part 1 · covers the tooling as it actually is

What the tools really do, in their vendors' own words

6 min live

Before the research, the honest inventory. The first-party AI surface in unit testing is smaller than the marketing suggests, and the one genuinely engineered system is for browser end-to-end work rather than units.

LiveThe four tools, and the catch each vendor documents6 min▶

Copilot's /tests command. "Generate unit tests for the selected code", available in VS Code, Visual Studio, JetBrains and Xcode. GitHub's own caveats, and they are unusually direct: the tests "may not cover all scenarios", complex scenarios "require more detailed prompts", and "You should always review the generated code." Note what the command takes as input. The selected code. That is the ordering problem, shipped as a keyboard shortcut.

Playwright Test Agents. Three agents. The planner writes a Markdown test plan. The generator turns that plan into real test files, verifying selectors live rather than guessing them. The healer repairs failures. This is the most seriously engineered AI testing system in the landscape, and it comes with three documented catches: agent definitions are static files that go stale on every Playwright upgrade, generated tests "may require subsequent repairs", and the healer "can skip tests if it determines underlying functionality is broken".

That third catch deserves a policy, not a note. A skipped test does not fail the build. It leaves you a green suite that is testing nothing in exactly the area where something was actually broken. If you run the healer, make skipped-test counts a visible number that a human signs off on, the same way you would a deleted test.

Vitest. The only unit framework of the three with first-party AI guidance, and it is guidance rather than a tool. It is worth reading precisely because it documents the real failure modes: models trained on Jest emit jest.fn() and fail, mocks leak between tests unless you set restoreMocks: true, AI "defaults to excessive test doubles", and agents hang forever unless they use vitest run rather than watch mode.

Jest and pytest. No first-party AI features documented. Say it that way, not as "none exist" - the accurate claim is about what the official docs carry, and both are large ecosystems with plenty of third-party tooling around them.

Self-studyThe excessive-mocks trap, and why it makes session 2 worse4 min▶

Vitest's line that AI "defaults to excessive test doubles" is not a style complaint. Follow it through to what it does to your suite and it lands directly on last session's material.

A test full of doubles asserts on the interactions between the parts rather than on the behaviour of the whole. Which helper was called, with what, how many times. That is the definition of a change detector: it is testing the current implementation rather than the specification, so it goes red on a harmless refactor and it goes green while the actual output is wrong.

  • The tell is the same one you learned last week. Refactor without changing behaviour. If the generated tests go red, the generator gave you change detectors.
  • The fix is upstream, in the prompt. Ask for tests that assert on returned values and observable effects, and say explicitly that doubles are only for genuine boundaries such as the network, the clock and the filesystem.
  • Set restoreMocks: true before you generate anything. Otherwise leaked mocks make the failures order-dependent, and you will spend the evening debugging the harness instead of reading the tests.
Part 2 · covers the ordering problem

The order decides the result, and the gap is roughly double

7 min live

This is the most important part of the session and possibly of the course, because it is a free improvement. Same model, same module, same amount of work. The only thing you change is what the test was written from.

LiveStudy one: tests written after faulty code inherit the fault5 min▶
✗ The finding you cannot unsee Konstantinou, Tambon and Papadakis, 2026. Tests generated AFTER faulty code detect 14% of faults. Tests generated INDEPENDENTLY detect 25% of faults. Their sentence: "incorrect implementations and tests are mutually consistent, masking defects rather than revealing them." And the part that closes off the easy escape: the effect "persists across different prompting strategies and multi-step workflows."

Sit with "mutually consistent" for a second. The test and the code are not in disagreement, which is precisely the problem. A test is only useful because it is an independent statement of what should happen, checked against a separate statement of what does happen. When both statements come from the same source, the check is circular and the green is meaningless.

The second half is the important half for anyone planning to prompt their way out. Better prompts did not fix it. Multi-step agent workflows did not fix it. The ordering is upstream of prompt craft, which is unusual and worth saying out loud: this is not a skill issue, it is a sequence issue.

LiveStudy two: eleven models, and the mitigation with evidence5 min▶

Huang and colleagues ran the same question across eleven models, which matters because it rules out "that is just one model being bad."

  • Prompting with correct rather than incorrect code improved test accuracy by 57 percent, coverage by 12 percent, and bug detection by 24 percent. The quality of what you feed in propagates straight through to the quality of what you get out, and it propagates hardest into the thing you care most about.
  • On real-world examples, tests generated for incorrect code had a 47 percent worse bug detection rate. The effect is not confined to tidy benchmark problems.
  • The mitigation, and this is the practical one: supplying a natural-language description of intent recovered 34 percent bug detection. Not a new model. Not a longer prompt. A written statement of what the code is supposed to do.

★ That last bullet is your homework paying off. The half page you wrote in session 2 is the natural-language description of intent. You already have it. The rule is simply: hand the generator that, and do not hand it the implementation until the tests exist.

Part 3 · covers what raw generation yields at scale

Meta ran this for real, and the value was in the filter

6 min live

Nothing above says do not generate. Here is the largest published deployment, with numbers that are both genuinely good and considerably less than the headline suggests.

LiveThe architectural lesson, which is the transferable part5 min▶

Read the funnel honestly. Three quarters of generated test cases built at all. Just over half passed reliably. Only a quarter increased coverage. And yet 73 percent of the recommendations that survived were accepted by engineers, which is an extraordinary acceptance rate for machine-written code.

Both halves of that are true at once, and the bridge between them is the filter. Meta's own framing: the system "verifies that its generated test classes successfully clear a set of filters that assure measurable improvement over the original test suite, thereby eliminating problems due to LLM hallucination."

The transferable design, and you can build a small version this week. Do not treat generated tests as output. Treat them as candidates, and put a gate between the generator and your suite. A candidate enters only if it builds, passes reliably on repeated runs, and demonstrably improves the suite on a measure you have chosen in advance. Everything else is discarded without discussion. Meta's number for that improvement measure was coverage. Session 4 gives you a better one.

The academic benchmark, for calibration. TestPilot, evaluated on 25 npm packages and 1,684 API functions, reached a median of 70.2 percent statement coverage and 52.8 percent branch coverage. Solid numbers, and worth holding next to session 1: coverage is what these systems are usually optimised for, and coverage is the metric the research says does not measure suite quality.

Build-along

Generate it twice and compare what each set catches

★ 22 min · everyone builds

Your module, two orderings, one comparison. Use whatever generator you already have. The finding is about the sequence, not about the tool, so Copilot, an agent, or a chat window all work.

Plant a bug first, and write it down. Make one small deliberate mistake in the module. Move a threshold by one, flip a comparison, drop an edge case. Note exactly what you did on paper, then close the file. This is your known fault, and without it you have no way to grade either test set.

Ordering A: generate from the code. Give the generator the module as it now is, bug included, and ask for unit tests. Do not mention the specification, do not describe intent. This is the default workflow and it is what /tests on a selection does.

Run set A and look at the colour. Green, most likely. Read the assertions around your planted bug. In a good number of cases you will find the bug written down as the expected value, which is "mutually consistent" in the flesh.

Ordering B: generate from the spec. New session, no history. Give it only your half page from session 2: inputs, outputs, thresholds, error cases. Ask for tests against that description. Withhold the implementation entirely.

Now run set B against the buggy code. This is the moment worth staying quiet for. If the spec named the threshold you moved, something in set B should be red, and the failure message should point straight at your planted fault.

Fix the bug and re-run both. Set B should go green. Set A was already green and stayed green, which is the entire lesson in two runs.

Apply the filter to both sets. Keep a candidate only if it builds, passes reliably twice in a row, and adds something the suite did not already check. Delete the rest without negotiating with yourself. This is your small TestGen-LLM.

✗ Ordering A, the prompt almost everyone starts with Here is my pricing module. Write unit tests for it. [the whole implementation pasted below] The model has exactly one source of truth: the code. Every threshold it asserts on is read off your implementation, including the one you got wrong. Result: 14 percent of faults detected.
★ Ordering B, the same work in a different sequence Write unit tests for a pricing function with this specification. Do not ask for the implementation, I am withholding it on purpose. price(basket, memberSince) returns the total in whole pence. Members, meaning memberSince < 2020, get 10 percent off. An empty basket costs 0. A negative quantity is rejected with an InvalidBasket error. Put an assertion exactly on every threshold named above, including memberSince of exactly 2020. Assert on returned values, not on which helpers were called. Use test doubles only for the clock.

What good looks like here. Short sentences, one promise each, every threshold stated as a number. If your spec runs long and winding, the generator will pick a subset of it and you will not know which subset. Splitting a twenty-word sentence into two ten-word promises usually buys you two more tests.

Every test in the module asserts on something Session 2's audit, finished. Zero assertion-free tests left in this one module.
You can name the fault each test would catch One sentence per test, ideally in the test name. Partly counts here, nobody has all of them.
A behaviour-preserving refactor leaves the suite green The change-detector tell. If a few still go red, that is a known list, not a failure.
Generated tests come from the spec, not the finished code Tonight's rule. If you have run the experiment once, that is enough to score partly.
Nothing generated enters the suite without clearing a filter Meta's lesson at small scale. Even a two-line checklist you apply by hand counts.
Homework

Before session 4

30 min
  1. Finish the two-ordering experiment properly. Three planted bugs rather than one, and record for each whether set A caught it and whether set B caught it. Six results. That table is the most persuasive thing you will ever show your team about generated tests.
  2. Write your filter down as a checklist. Three or four lines. Builds, passes twice, adds a check the suite did not have, asserts on a value rather than an interaction. Put it in the repository next to the tests, not in your head.
  3. Turn your spec into the standing prompt. Save the ordering B prompt as a file in the repo. Next time somebody generates tests for this module, they start from the spec because the spec is what is sitting there ready to paste.
  4. If you use Vitest, set restoreMocks: true now. Two minutes, and it removes a class of order-dependent failure that will otherwise be blamed on the generator.
  5. Bring both test sets to session 4. Unchanged. You are going to run mutation testing on them, and the scores are going to be more interesting than the coverage numbers were.
Check yourself

Three questions

Clear all three and session 3 gets stamped in your passport.

1 · Tests generated after faulty code detected 14 percent of faults, against 25 percent for tests generated independently. Why?

Konstantinou, Tambon and Papadakis: "incorrect implementations and tests are mutually consistent, masking defects rather than revealing them." Their study also found the effect "persists across different prompting strategies and multi-step workflows", so better prompting does not rescue it.

2 · Playwright's healer agent repairs failing tests. Which documented behaviour needs a policy around it?

Playwright documents that the healer "can skip tests if it determines underlying functionality is broken". A skipped test does not fail the build, so you are left with a green suite that is testing nothing precisely where something broke. Make skipped counts visible and human-approved.

3 · At Meta, 75 percent of generated test cases built and only 25 percent increased coverage, yet 73 percent of surviving recommendations were accepted. What made that work?

Meta's framing: the system "verifies that its generated test classes successfully clear a set of filters that assure measurable improvement over the original test suite, thereby eliminating problems due to LLM hallucination." The generator is the cheap part. The gate is the engineering.
